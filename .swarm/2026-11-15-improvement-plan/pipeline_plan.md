# Pipeline candidates: verification and minimal plan

## 1. Historical incident picks a current trace — confirmed by source

`incident-detection/ingest/reader.py:81` returns a preferred ID unchanged; otherwise it searches error traces and then all traces using only a lookback. `ingest/clients/tempo_client.py:112` and `:132` calculate both bounds from `_utcnow()`. `reader.py:118-144` separately builds a window from `around`, samples traces in that window, and prepends the selected trace by ID if missing. Thus a delayed/historical incident with no preferred ID can acquire a current trace outside its window; prepending is conditional on a nonempty ID absent from sampled spans. A preferred ID intentionally bypasses search and is also fetched without a window check; whether that persisted ID should be validated is an unresolved policy question, not needed to correct automatic selection.

Callers: `ingest/trigger/app.py:169-191` supplies alert start (which may be historical) with no preferred ID; `rca/orchestrator.py:233` supplies the persisted preferred ID, which can be absent. No other `resolve_trace_id` callers found. Tempo search methods also appear in client tests and may be public: preserve their existing default relative-to-now behavior. Existing `tests/test_client_hardening.py` covers TraceQL error query; `tests/test_adapters_http.py` covers search failures.

Smallest compatible fix: allow explicit start/end bounds for error and fallback searches, and have reader resolve using its actual `Window`; reuse existing `_search_traceql` and `_search` / `search_traces_in_window`, retaining recent-search defaults for existing callers. Preserve error-first fallback and preferred-ID behavior. Tests: mocked historical search checks both exact bounds, error-first and fallback, missing result, preferred bypass, and no current trace prepended; keep error query and client default tests passing. Search errors currently return empty lists and should retain that behavior. Tempo serializes timestamps to integer seconds, so subsecond request bounds are not exact at backend level.

## 2. RCA persisted analysis bounds rounded — confirmed, with qualification

`rca/orchestrator.py:219-239` rejects missing or nonpositive windows and always closes the reader. It sets `around=end-1 minute`, then floors `(end-start-1 minute)` to whole minutes and clamps to zero; `reader.py:117-120` reconstructs start as `around-lookback` and end as `around+1 minute`. End is preserved; start moves forward by the remainder for windows at least one minute. For a valid window shorter than one minute, clamping moves reconstructed start *before* persisted start. This is duration truncation, not rounding timestamps themselves. Loss/expansion affects all retrieved telemetry and the RCA offsets (`rca/adapter.py:31,154`). Existing `tests/rca/test_orchestrator.py:102-104` covers only whole-minute input.

Smallest compatible fix: let `read_incident_window` accept explicit window bounds as an optional paired input while retaining existing `around`/lookback interface for trigger and other callers; have orchestrator pass persisted bounds directly and retain existing validation and cleanup. Construct the same `Window` once, then use it for trace resolution and all adapters. Avoid rounding or altering stored data. Update fake-reader assertions and test fractional-minute and under-one-minute bounds, whole-minute compatibility, invalid/missing-window rejection, and close on failures. Review any caller mocks for added keywords (`tests/rca/test_orchestrator.py`, `tests/test_trigger_service.py`).

Dependency: implement exact reader-window support before or together with window-scoped trace selection so both use one set of bounds. No schema migration or new dependency is indicated. This is source analysis only: no pytest, backend, live-cluster, or endpoint behavior was verified. Backend timestamp granularity and whether preferred traces should be constrained remain open.

KISS: Pass existing incident bounds through the existing reader and Tempo search paths; preserve current defaults and avoid new services or data models.
