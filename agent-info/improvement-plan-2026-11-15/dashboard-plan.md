# Dashboard correctness and persistence plan

Planning only; application code unchanged. Findings are source-confirmed, not runtime-verified.

1. **Rolling inbox window — confirmed.** `dashboard/frontend/src/pages/IncidentInbox.jsx` stores `Date.now()` once, so relative `filters.minutes` remains anchored at mount even when stream updates arrive. Use a minute-aligned timer only while relative filtering is active; clean it up, keep explicit `from`/`to` fixed, and retain stable minute-rounded query bounds. Check the `useFetch` query and stream refresh callers; add a Vitest fake-clock regression proving the window advances without remount and stops on unmount, plus fixed-range coverage. No dependencies.
2. **Joined incident status — confirmed.** `dashboard/backend/db.py` `_pg_list_joined` flattens `i.status` into `report`, but `_normalize_report(r, None)` only checks `inc.status`; a resolved incident without report `resolved_at` appears open. Read `report.status` as well, preserving file-join precedence and resolved fallback. Exercise PostgreSQL joined, file joined, orphan and unresolved cases; `routers/incidents.py` filtering and `ack_store.lifecycle_for`/`routers/stats.py` consume the normalized status. No migration.
3. **Remediation rate — confirmed.** `dashboard/backend/routers/stats.py` reads top-level status counts, whereas `remediation_store.py` `stats()` returns `by_status`. Read counts there and retain the existing succeeded/(succeeded+failed+rolled_back) denominator and null when empty. Test mixed statuses and zero denominator through stats; `frontend/src/pages/Statistics.jsx` consumes the result. Clarify separately if product intends a time/service-filtered metric: current remediation counts are global.
4. **Acknowledgement persistence — confirmed deployment mismatch.** `dashboard/backend/ack_store.py` writes `.run/incident_acks.json`; dashboard Helm deployment has `readOnlyRootFilesystem: true`, and local lock cannot coordinate replicas. Store ack/snooze keyed by incident ID in Postgres when configured, using existing `DashboardStore` psycopg connection conventions (no dashboard pool found), atomic upsert and shared reads; retain file mode explicitly for local development only, never silently fall back on database errors. Add schema to both `incident-detection/helm/postgres/templates/configmap.yaml` and `schema-migrate-job.yaml`, plus required grants in `rca-engine-grants-job.yaml` following existing patterns. Wire `routers/incidents.py` list/detail/ack/snooze and `routers/stats.py` merges; avoid per-item connections via bulk reads if necessary. Verify persistence across store instances, concurrent updates, deployment read-only filesystem, database failure, and local fallback. Existing file acknowledgements require an explicit migration decision before rollout; do not silently discard them. Migration and grants precede deployment.
5. **Feedback false success — confirmed.** `dashboard/backend/db.py` `update_feedback` catches PG errors and returns fabricated feedback, also returns success without PG and for unmatched IDs; `routers/incidents.py` reports success unconditionally. Require a real persisted update and detect zero affected rows; surface database failures and not-found as appropriate API errors. Define explicit durable local behavior or return an unsupported/error response in file mode rather than pretending success. Test success, missing report, write failure and file mode; verify `frontend/src/pages/IncidentInvestigation.jsx` displays failure and refreshes only on success. No new dependency.

Order: status and stats are independent; ack storage requires schema/grants first and changes shared readers; feedback is independent. Frontend clock change is independent. Focused backend tests and frontend Vitest/build checks should accompany implementation; live Postgres and Helm checks are separate integration evidence.

KISS: Reuse current stores and database conventions, with one durable acknowledgement table and no new service or dependency.
